# SMS notifications for critical detections

**Current provider: SMSlenz.** Follow [SMSlenz registration and sample testing](SMSLENZ_SETUP.md)
for the selected free trial. The Twilio instructions below remain an alternative:
set `SMS_PROVIDER=twilio` to use them. The local `.env` selects SMSlenz and limits
automatic samples to four queued submissions per backend process. See the SMSlenz
guide for the budget, credential fields, and test steps.

Critical animal-human proximity alerts and drowning alerts can now submit SMS
messages to every configured recipient through Twilio. Ordinary person detection,
safe states, and warning alerts do not send SMS. The existing detection rules decide
when a situation is critical; this change adds a notification to that event.

The two supplied Sri Lankan numbers are already in the local `.env` file in
international format. This file is ignored by Git. Credentials remain on the
backend and are never sent to the browser.

## Configure Twilio

### Free samples and current trial restrictions

Checked on October 17, 2026: Twilio's current
[trial account documentation](https://www.twilio.com/docs/usage/trials#supported-countries)
does not list Sri Lanka as a supported trial country. New trials also restrict SMS
to predefined Twilio templates and the sign-up country. The custom critical-alert
messages generated by this project are not supported by those new trial terms.
A new free trial cannot be relied on for custom alerts to the supplied +94 numbers.
The live setup below may require an upgraded account and approved sender; it is
not a promise of free phone delivery. Do not upgrade or buy a number for a zero-cost
demo.

You can test this project's notification logic for free without an account:

```powershell
python -m backend.test_sms --simulate
```

This runs synthetic animal-human and drowning critical events through the actual
notification queue, message formatting, recipient routing, and cooldown logic.
It uses a local fake transport even if live credentials are present. It prints
four simulated notifications for the two configured numbers, checks repeated
critical alerts and warnings are suppressed, and never contacts Twilio or sends
messages to phones. It does not run AI inference on the sample videos.

For a simple message preview, use `python -m backend.test_sms`. Keep
`SMS_ENABLED=false` during free testing. Neither command needs Twilio credentials.

Twilio's [test credentials](https://www.twilio.com/docs/iam/test-credentials)
also simulate API requests without phone delivery, but the new Console cannot
create them. Existing legacy test credentials remain supported. They are distinct
from a trial account's live Account SID/Auth Token. They are not a way to receive
free SMS on the supplied phones.

### Live phone delivery

1. Create or sign into your [Twilio account](https://www.twilio.com/console).
2. Obtain the Account SID and Auth Token. Enable Sri Lanka in
   [SMS geographic permissions](https://www.twilio.com/docs/messaging/guides/sms-geo-permissions),
   and ensure the account is eligible to send custom SMS to Sri Lanka. New trial
   accounts are insufficient under the current restrictions above. An existing
   legacy account may have different terms; confirm those in its Console.
3. Arrange a sender suitable for Sri Lanka. Twilio's
   [Sri Lanka SMS guidelines](https://www.twilio.com/en-us/guidelines/lk/sms)
   state that Dialog, Etisalat, and Hutchison networks require a registered
   alphanumeric Sender ID and block unregistered/numeric senders from July 29,
   2026. A purchased international number alone may therefore be insufficient.
   Confirm your alert use case and sender registration with Twilio before enabling
   live alerts. This application accepts an approved alphanumeric Sender ID, a
   supported international sender number, or a Messaging Service configured with
   the appropriate registered sender.
4. Install the backend requirements using the Python environment that runs it:

   ```powershell
   python -m pip install -r backend/requirements.txt
   ```

5. Open `.env` in the project root and fill in:

   ```dotenv
   TWILIO_ACCOUNT_SID=AC_your_actual_account_sid
   TWILIO_AUTH_TOKEN=your_actual_auth_token
   TWILIO_FROM=YourSender
   ```

   `YourSender` is a placeholder: use the Sender ID Twilio has actually approved.
   Account SIDs must be `AC` followed by 32 hexadecimal characters. Alternatively,
   leave `TWILIO_FROM` empty and set `TWILIO_MESSAGING_SERVICE_SID` to the configured
   `MG...` service SID. The service takes precedence when both are set.
   Add/change numbers with `SMS_RECIPIENTS`, separated by commas. Local Sri Lankan
   mobile numbers beginning with `07` are converted to `+94` format automatically.
   `.env.example` is a reusable template without personal recipient numbers.

## Test before enabling automatic alerts

Run these commands from the project root. They do not load AI models or start video
streams. The first command previews a clearly labeled test message without making
network requests:

```powershell
python -m backend.test_sms
```

The following command actually submits one test SMS to each configured number;
Twilio/carrier charges may apply. It works while `SMS_ENABLED=false` so you can test
the setup without starting automatic notifications:

```powershell
python -m backend.test_sms --send
```

Check Twilio's message logs and both phones. A returned SID or `queued`/`accepted`
status means Twilio accepted a submission, not that the phone received it. Check
`delivered`, `undelivered`, or `failed` in Twilio's logs to confirm the final result.
The application does not host delivery callbacks or independently verify handset
receipt. See [Twilio's Messages API](https://www.twilio.com/docs/messaging/api/message-resource).

## Enable automatic notifications

Set `SMS_ENABLED=true` in `.env`, then restart the backend. Operating-system
environment variables take precedence over `.env` values. Use the launcher's Python
environment if you have multiple installations.

**The application automatically plays its sample videos at startup. Their critical
detections will also send real SMS when enabled.** Keep SMS disabled during routine
development or use an appropriate live source. Detection is independent of the
browser: notifications can be sent even when the dashboard is closed or its buzzer
is muted. Ordinary human presence is currently safe and does not trigger SMS.

Open dashboard Settings to see SMS readiness, masked recipient numbers, missing
settings, and recent submission results. Status refreshes every five seconds while
Settings is open. A read-only status API is also available at
`GET /api/notifications/sms/status`. No credentials or full phone numbers are
returned by this endpoint. Actual test sends use the local command above.

## Repeat alerts and failures

- The first saved critical alert is queued immediately for each number.
- Further alerts of the same channel and type are limited to one submission per
  recipient every `SMS_COOLDOWN_SECONDS` (default 300 seconds / five minutes).
  Continuing danger can generate another SMS after the cooldown. A drowning alert
  has its own cooldown and is not suppressed by an animal alert.
- Sending runs on a separate background thread, so a slow provider does not block
  video processing, the dashboard alarm, or incident recording.
- If a request fails, the other recipient is still attempted. A later critical
  detection can retry the failed recipient after `SMS_FAILURE_BACKOFF_SECONDS`
  (default 60 seconds); it does not resend immediately every frame. There are no
  autonomous retries if detections have stopped.
- A timeout can be ambiguous: Twilio may have accepted a request before the
  connection failed. Check Twilio's logs before manually retrying a test.
- The queue is bounded at 32 submissions. Network requests time out after
  `SMS_HTTP_TIMEOUT_SECONDS` (default 10 seconds, maximum 30). Failures are shown in
  Settings and the backend console with sanitized provider codes.
- Queue, cooldowns, and submission statuses are kept in memory. Pending submissions
  are discarded at shutdown, and cooldowns reset on backend restart. Incident
  records and snapshots continue to use the existing SQLite storage. This is not a
  persistent SMS delivery outbox or a guaranteed delivery service.

The SMS includes the site name, event type, animal classes when relevant, estimated
distance when available, and the incident timestamp from the backend's clock.
Messages are ASCII and at most 160 characters to limit segmentation. Change
`SMS_SITE_NAME` to a short camera/site name so recipients know which location to
check. The normal dashboard alarm remains active if SMS is unavailable.
